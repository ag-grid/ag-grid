# SSRM streaming benchmark: report

> **Indicative only.** Every number here was measured in headless Chromium on a shared CI runner (4 cores of an AMD EPYC 7763, software rendering, no physical display). A frame-rate pass means the main thread kept up, not that a screen showed it. Re-run on the target hardware before quoting a number (see _Reproduce_).

This report covers a trading-desk streaming workload on the Server-Side Row Model (SSRM): live top inserts, per-cell streaming updates, all sorting, filtering, grouping and aggregation on the server, many grids per screen and wide column sets. The demo and harness are in this folder (`README.md`). Grid source was not changed.

## Summary

All numbers below are from the run recorded in `results/results.json` (git `9b2a32a`, 22:32 to 22:42 UTC on 2026-11-26). The baseline scenario S1 shows 57 rows x 58 columns, just over the 50 x 50 the requirement names, with a top insert every 75 ms and 5 updates/s per visible cell. Only rows inside the viewport are sampled: the grid renders a few rows below it that View Subscription does not stream to.

### Meets as-is

- **R1, server-side operations.** A header-sort click, a number filter, a text filter and grouping each reached the backend as `sortModel`, `filterModel` and `rowGroupCols`. With 500 ms backend latency, no frame before the response showed the rows reordered, and afterwards every rendered row matched the backend's own result for that sort and filter, row by row (S11). The demo sets `serverSideEnableClientSideSort: false`.
- **R3, refresh rate with more than 50 x 50 visible.** 5 content refreshes/s at 44 fps, with a longest frame of 83 ms (S1). With 116 rows x 62 columns visible (S1L) it managed 4.3 refreshes/s at 20 fps, with a longest frame of 233 ms.
- **R5, backend order, for arrival time newest first.** The rendered arrival order matched the backend in all 29 checks (S1). A new top row reached the page 8.6 ms (p95) after its transaction applied; with async transactions, add the queue time before that, 138 ms (p95). The check reads each row's `row-index` attribute, not its painted position. Inserts under any other sort or a filter were not measured (see below).
- **R6, aggregation pace.** Every group-row and grand-total value sent was on screen, or replaced by a later value that was, within 131 ms (p95 for both), inside one 200 ms update interval (S6).
- **R9, row counts.** Rows were correct at the top, middle and end with 100,000 and 100,000,000 backend rows (S10a, S10b). In both cases the grid scales its row container to a scroll height of 1,000,023 px.
- **R10b, 2,000 columns.** Sending every field: 3.99 refreshes/s at 17 fps, 26,673 bytes per row (S8c). Trimming to the visible columns cut that to 791 bytes per row at a similar rate (S8d), but after a horizontal scroll 9,000 of 9,072 cells were blank until a refetch filled them 159 ms later. The payload cost of sending everything falls on the backend and network, which this benchmark does not model: the mock backend spent 118 ms/s building full rows against 17 ms/s trimmed.

### Meets only with workarounds

- **R4, top inserts (partial).** 13.19 inserts/s were applied against 13.3 requested, with 5 refreshes/s (S1). But every insert destroyed one row element and created a new one: about 13 added and 13 removed per second, and no element was re-keyed to another row. Measured workarounds: keep `animateRows` off (on, the frame rate fell from 44 to 13 fps, S4), and keep the visible area near 50 x 50 (with 116 x 62 visible, inserts fell to 7.56/s, S1L). Synchronous transactions took 14.3 ms (p50) and 31.2 ms (p95) each, including the redraw (S3).
- **R7, 500-row window (partial).** Over 40 s of inserts, the default cache (`cacheBlockSize` 100, `maxBlocksInCache` -1) grew to 581 loaded nodes and was still growing by about 9/s (S5a); 500 / -1 grew to 861 (S5d). `maxBlocksInCache` 5 stopped at 500 nodes once five blocks were loaded (S5b), and 500 / 1 held at 500 throughout (S5c). The verdict generator counts S5b as unbounded because it was still growing in the second half of the window, before it reached its cap; the S5b numbers above show it was capped.
- **R8, selection across pause and resume (partial).** The five selected rows were still selected after resume, at their new indexes (5-9 moved to 55-59). The cell range stayed on indexes 5-9, now covering other rows (S7). The workaround, re-creating the range from the row ids, was not measured. Applying the 55 buffered transactions on resume (async, then one flush) took 534 ms, with a longest frame of 667 ms.

### Does not meet

- **R2, per-cell update rate (narrowly).** At 5 updates/s requested, the rendered per-cell rate was 4.82/s (p50; p10 4.69/s), and every row in view changed at least once a second (S1). With updates alone the rate was 5.01/s (S1u), so the shortfall comes with the inserts. A likely cause is that a row inserted at the top gets no updates until View Subscription reports it, but the harness does not separate this. Above 5/s the grid fell further behind: 10/s requested rendered 6.67/s, 20/s rendered 6.46/s and 80/s rendered 4.7/s (S12 sweep).
- **R10a, 100 live grids.** With 100 grids live on one screen, each showing about 10 rows x 4 columns, the slowest grid refreshed 0.5 times a second at 16 fps (S9c). The feeds themselves were starved: grid 1 delivered 0.8 inserts/s and 0.8 update ticks/s against 13.3 and 5 requested. A reduced feed (2 inserts/s and 2 updates/s per cell per grid) was starved to the same level and did not help (S9d). For comparison, 16 grids refreshed 2.59 times a second and 4 grids 3.89 times a second (S9b, S9a).

### Unmeasured

No requirement is wholly unmeasured. The parts that are are listed under _What this benchmark could not show_.

## Where the failures come from, and proposed fixes

These are proposals only. Nothing was changed in the grid for this work.

### Top inserts destroy and create a row element instead of re-using the one that left (R4)

- **Measured:** row elements added and removed per second equal the inserts applied per second, and no row element was ever re-keyed to another row id (S1, S1i, S4).
- **Code path:** `RowRenderer.createOrUpdateRowCtrl` (`packages/ag-grid-community/src/rendering/rowRenderer.ts`, around line 1301) re-uses a row controller only for the same row id (`rowsToRecycle[rowNode.id]`). Controllers left over are destroyed in `destroyRowCtrls` (around line 1343); with `animateRows` they are first kept as zombies for the fade-out.
- **Proposed fix:** when a redraw both removes a row id and adds a new one, hand the departing `RowCtrl`/`RowComp` to the new row node and refresh its cells, instead of destroying it and building a new one. This needs a "re-key" path through `RowCtrl` (row id attribute, row-level classes, cell renderers), similar to how `cachedRowCtrls` already keeps controllers alive for later re-use.

### Each transaction re-indexes every loaded node (R4)

- **Measured:** synchronous transaction apply time in S3 (`txSyncApplyMs` in `results.json`). That time includes the grid's synchronous redraw, so it is an upper bound on the store cost alone; the harness does not separate the two.
- **Code path:** `LazyCache.insertRowNodes` (`packages/ag-grid-enterprise/src/serverSideRowModel/stores/lazy/lazyCache.ts`, around line 1270) filters the whole node map for `index >= addIndex`, then deletes and re-adds each moved node. A top insert moves every loaded node, so the cost grows with the number of loaded rows. `removeRowNodes` does the same in the other direction.
- **Proposed fix:** keep a per-store index offset (or another structure with cheap index shifts) so that inserting at the top shifts one offset instead of rewriting every node's index.
- **Workaround today:** batch inserts. One transaction with several rows in `add` costs one re-index pass, and `applyServerSideTransactionAsync` already batches by `asyncTransactionWaitMillis` (default 50 ms).

### Loaded nodes grow under top inserts with an unlimited cache (R7)

- **Measured:** with `maxBlocksInCache` -1 (the default) the loaded node count grew at about the insert rate for the whole 40 s window (S5a, S5d). With a block limit it stopped at the limit (S5b at 5 x 100, S5c at 1 x 500).
- **Code path:** inserts at index 0 push loaded nodes to higher indexes (`LazyCache.insertRowNodes`), and the oldest row removed at the far end was never loaded, so each insert adds one loaded node. `LazyCache.purgeExcessRows` (around line 735, run from `setDisplayIndexes`) drops blocks beyond `maxBlocksInCache`, but returns early when there is no block limit: `StoreFactory.getMaxBlocksInCache` (`stores/storeFactory.ts`, around line 58) turns a negative `maxBlocksInCache` into no limit.
- **Proposed change:** none needed in the grid if the window is set with `maxBlocksInCache`. Whether an unlimited cache should still drop rows pushed far past the viewport is a design question, not a defect.
- **Workaround today:** set `maxBlocksInCache` (for example `cacheBlockSize: 100, maxBlocksInCache: 5`, or `500` and `1`). Dynamic and auto row height need `maxBlocksInCache` unset, so this rules those out.

### Cell ranges do not follow rows when they move (R8)

- **Measured:** after pause and resume with inserts in between, the selected rows were still selected (by id) at their new indexes, but the cell range stayed on the same row indexes, now covering other rows (S7).
- **Code path:** `CellRange.startRow` / `endRow` are `RowPosition { rowIndex, rowPinned }` (`packages/ag-grid-community/src/interfaces/IRangeService.ts`, around line 76). Row selection is stored by id (`getServerSideSelectionState`).
- **Proposed fix:** store a range's start and end rows by row id (with the index as the fallback for rows without ids) and resolve the indexes when drawing.
- **Workaround (not measured):** the app records the range's row ids before pausing and re-creates the range with `api.addCellRange` from the rows' new indexes after resume.

### Main-thread cost of many live cells and many grids (R2, R10a)

- **Measured:** see the R2 and R10a rows and the S1L, S9 and S12 scenarios. With 100 grids the feeds' own timers were starved (S9c), so the main thread, not the feed, is the limit. The mock backend's share of the main thread is recorded per scenario (`feed.backendMsPerS` in `results.json`) and was under 2 % in S1.
- **Code path:** each update transaction refreshes every rendered cell of every updated row. The grid has no per-frame budget, so updates queue behind long tasks.
- **Proposed fix:** profile S1L and S9c in a real browser first, to find the dominant cost (cell refresh, value formatting, style recalculation, layout). Then consider coalescing updates per frame (only the last value per cell, applied on `requestAnimationFrame`) and skipping cells whose formatted value did not change.
- **Workarounds (not measured):** send only the changed columns in update rows, lower the per-cell rate for grids that are not in focus, and set `viewSubscriptionActive: false` on grids that do not need to be live.

## What this benchmark could not show

- Real display behaviour. Headless Chromium has no display and renders in software, so paint and compositing costs are not representative.
- The customer's backend. The mock backend runs in the browser on the same thread as the grid; its cost is recorded so it can be subtracted.
- Every row updated once a second across the whole store. View Subscription streams only the rows in view, and only those are measured (R2).
- Sorting or filtering 100m rows. The mock backend materialises at most 200,000 rows for a non-arrival sort or a filter (`MAX_MATERIALISE` in `src/backend.js`). R9 covers scrolling at 100m in the default arrival order.
- Live inserts under a non-arrival sort or a filter. The demo falls back to `refreshServerSide({ purge: false })` once a second in that case (`src/grids.js`); this path was not measured.
- Row order while `animateRows` is on. In S4 all 9 order checks reported a mismatch, most likely from rows still fading out with their old `row-index`; this was not investigated, and R5 is judged on S1.
- Insert rate over a long session with the default cache. S1 uses the default unlimited cache, and its loaded nodes grew from 150 to 257 during the 10 s window. Each insert re-indexes every loaded node, so the 13.19 inserts/s of S1 may not hold over minutes unless `maxBlocksInCache` is set. This was not measured.
- The harness's own cost with many grids. The feed-off control (S0) covers one grid; with 100 grids the per-frame sampling reads about 100 times as many rows, and no 100-grid control was run, so part of the R10a shortfall may be the harness.
- `pauseWhenHidden` with many grids. In S9 every grid is on screen, so pausing hidden grids was never exercised.

## Open questions for the customer

From the requirements:

1. Do they need push-style top inserts (SSRM transactions), or only server-driven loads?
2. Can the backend trim columns to the visible set? What is the real per-row payload?
3. Can the backend send incremental updates keyed by a stable row id?
4. Is group expand/collapse needed in the UI? Is cell-range selection required, or only row selection?
5. Which browser and hardware is the 5-10 updates/s benchmark measured on?
6. How many of the 100+ grids are live at once?

Raised by the numbers:

7. Do the 50 x 50 visible cells and 5-10 updates/s per cell apply to one grid at a time, or to every live grid? With 100 grids live, each refreshed less than once a second.
8. Is re-using the row element a hard requirement, or is the concern the visible delay when rows move down? A new top row reached the page within about 150 ms of being sent (138 ms async queue plus 9 ms to render, p95), and every order check found the rows below already moved.
9. Must a cell range follow its rows while inserts move them, or only be restored correctly after a pause?
10. Do they need variable or automatic row heights? The only cache setting that held a 500-row window (`cacheBlockSize: 500, maxBlocksInCache: 1`) rules those out.
11. How long may a resume take? Applying 55 queued transactions through the async batch took 534 ms, with one frame of 667 ms.

## Reproduce

From the repo root, after `npm run bootstrap`:

```bash
yarn nx run-many -t build:umd -p ag-grid-community,ag-grid-enterprise
node testing/manual/ssrm-streaming-bench/run-bench.mjs
```

`results/results.json` records the machine, browser, AG Grid version and git commit of the run. A possible bug noticed while reading code for this work, `ViewportRowModel.isEmpty()` looking inverted, has been raised separately.
