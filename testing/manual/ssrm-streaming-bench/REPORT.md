# SSRM streaming benchmark: report

> **Indicative only.** Every number here was measured in headless Chromium on a shared CI runner (4 cores of an AMD EPYC 7763, software rendering, no physical display). A frame-rate pass means the main thread kept up, not that a screen showed it. Re-run on the target hardware before quoting a number (see _Reproduce_).

This report covers a trading-desk streaming workload on the Server-Side Row Model (SSRM): live top inserts, per-cell streaming updates, all sorting, filtering, grouping and aggregation on the server, many grids per screen and wide column sets. The demo and harness are in this folder (`README.md`). Grid source was not changed.

## Where the failures come from, and proposed fixes

These are proposals only. Nothing was changed in the grid for this work.

### Top inserts destroy and create a row element instead of re-using the one that left (R4)

- **Measured:** row elements added and removed per second equal the inserts applied per second, and no row element was ever re-keyed to another row id (S1, S1i, S4).
- **Code path:** `RowRenderer.createOrUpdateRowCtrl` (`packages/ag-grid-community/src/rendering/rowRenderer.ts`, around line 1301) re-uses a row controller only for the same row id (`rowsToRecycle[rowNode.id]`). Controllers left over are destroyed in `destroyRowCtrls` (around line 1343); with `animateRows` they are first kept as zombies for the fade-out.
- **Proposed fix:** when a redraw both removes a row id and adds a new one, hand the departing `RowCtrl`/`RowComp` to the new row node and refresh its cells, instead of destroying it and building a new one. This needs a "re-key" path through `RowCtrl` (row id attribute, row-level classes, cell renderers), similar to how `cachedRowCtrls` already keeps controllers alive for later re-use.

### Each transaction re-indexes every loaded node (R4)

- **Measured:** synchronous transaction apply time in S3 (`txSyncApplyMs` in `results.json`). That time includes the grid's synchronous redraw, so it is an upper bound on the store cost alone; the harness does not separate the two.
- **Code path:** `LazyCache.insertRowNodes` (`packages/ag-grid-enterprise/src/serverSideRowModel/stores/lazy/lazyCache.ts`, around line 1270) filters the whole node map for `index >= addIndex`, then deletes and re-adds each moved node. A top insert moves every loaded node, so the cost grows with the number of loaded rows. `removeRowNodes` does the same in the other direction.
- **Proposed fix:** keep a per-store index offset (or another structure with cheap index shifts) so that inserting at the top shifts one offset instead of rewriting every node's index.
- **Workaround today:** batch inserts. One transaction with several rows in `add` costs one re-index pass, and `applyServerSideTransactionAsync` already batches by `asyncTransactionWaitMillis` (default 50 ms).

### Loaded nodes grow under top inserts (R7)

- **Measured:** with `cacheBlockSize` 100 and `maxBlocksInCache` -1 (the defaults), with 100 / 5 and with 500 / -1, the loaded node count kept growing at about the insert rate (S5a, S5b, S5d). Only `cacheBlockSize` 500 with `maxBlocksInCache` 1 held at 500 (S5c).
- **Code path:** inserts at index 0 push loaded nodes to higher indexes (`LazyCache.insertRowNodes`). Passing `rowCount` on the transaction updates the store size, but no code was found that destroys loaded nodes pushed past the window; purging runs when blocks load (`LazyCache`, around line 761).
- **Proposed fix:** after a transaction, drop loaded nodes beyond the configured cache (and beyond `rowCount`), the same way a block purge does.
- **Workaround today:** `cacheBlockSize: 500, maxBlocksInCache: 1`, which holds exactly one 500-row block. Dynamic and auto row height need `maxBlocksInCache` unset, so this workaround rules those out.

### Cell ranges do not follow rows when they move (R8)

- **Measured:** after pause and resume with inserts in between, the selected rows were still selected (by id) at their new indexes, but the cell range stayed on the same row indexes, now covering other rows (S7).
- **Code path:** `CellRange.startRow` / `endRow` are `RowPosition { rowIndex, rowPinned }` (`packages/ag-grid-community/src/interfaces/IRangeService.ts`, around line 76). Row selection is stored by id (`getServerSideSelectionState`).
- **Proposed fix:** store a range's start and end rows by row id (with the index as the fallback for rows without ids) and resolve the indexes when drawing.
- **Workaround today:** the app records the range's row ids before pausing and re-creates the range with `api.addCellRange` from the rows' new indexes after resume.

### Main-thread cost of many live cells and many grids (R2, R10a)

- **Measured:** see the R2 and R10a rows and the S1L, S1u, S9 and S12 scenarios. The mock backend's share of the main thread is recorded per scenario (`feed.backendMsPerS` in `results.json`).
- **Code path:** each update transaction refreshes every rendered cell of every updated row. The grid has no per-frame budget, so updates queue behind long tasks.
- **Proposed fix:** profile S1L and S9c in a real browser first, to find the dominant cost (cell refresh, value formatting, style recalculation, layout). Then consider coalescing updates per frame (only the last value per cell, applied on `requestAnimationFrame`) and skipping cells whose formatted value did not change.
- **Workaround today:** send only the changed columns in update rows, lower the per-cell rate for grids that are not in focus, and set `viewSubscriptionActive: false` on grids that do not need to be live.

## What this benchmark could not show

- Real display behaviour. Headless Chromium has no display and renders in software, so paint and compositing costs are not representative.
- The customer's backend. The mock backend runs in the browser on the same thread as the grid; its cost is recorded so it can be subtracted.
- Every row updated once a second across the whole store. View Subscription streams only the rows in view, and only those are measured (R2).
- Sorting or filtering 100m rows. The mock backend materialises at most 200,000 rows for a non-arrival sort or a filter (`MAX_MATERIALISE` in `src/backend.js`). R9 covers scrolling at 100m in the default arrival order.
- Live inserts under a non-arrival sort or a filter. The demo falls back to `refreshServerSide({ purge: false })` once a second in that case (`src/grids.js`); this path was not measured.
- Row order while `animateRows` is on. In S4 the order check reported mismatches, most likely from rows still fading out with their old `row-index`; this was not investigated, and R5 is judged on S1.

## Reproduce

From the repo root, after `npm run bootstrap`:

```bash
yarn nx run-many -t build:umd -p ag-grid-community,ag-grid-enterprise
node testing/manual/ssrm-streaming-bench/run-bench.mjs
```

`results/results.json` records the machine, browser, AG Grid version and git commit of the run. A possible bug noticed while reading code for this work, `ViewportRowModel.isEmpty()` looking inverted, has been raised separately.
